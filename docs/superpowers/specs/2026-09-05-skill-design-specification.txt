     Skill Design Specification (SDS): A Composability, Safety, and
                Interoperability Layer for Agent Skills
                       draft-skill-design-spec-02

Abstract

   The Agent Skills format [BASESPEC] defines how a single skill is
   packaged (a directory, a SKILL.md file, optional scripts/,
   references/, and assets/ subdirectories) so that a model can discover
   and load it.  It is silent on how a family of skills, authored over
   time by possibly different people, should relate to one another so
   that the family behaves as one coherent, composable system rather
   than a directory of unrelated documents that happen to share a
   container format.  This document specifies that additional layer, top
   to bottom: a conceptual model of a skill as a typed, effectful
   function (Part 0); the layout, registry, versioning, and governance
   of a skill family (Part I); the reference kit every family ships and
   the rules for extending it (Part II); and the complete anatomy of a
   single conforming skill package, from frontmatter to fixtures (Part
   III).  Every normative rule carries a permanent identifier and a
   conformance tag stating whether a linter checks it, a human reviews
   it, or it is advisory.  It is written to be domain-independent; a
   companion document applies it to a software-development skill catalog
   as a worked example.

1.1.  Purpose and Scope

   This specification governs the design of a Skill Family: two or more
   skills intended to be authored, versioned, and used together,
   potentially chained so that one skill's output becomes another's
   input.  It applies regardless of domain; domain-specific choices made
   under this specification's rules are recorded in a domain-specific
   companion document, not here.

   This document does not specify:

   *  the internal reasoning process a model uses to decide whether a
      skill applies (that is the Base Spec's trigger-matching behavior);

   *  any particular domain's catalog of skills (see Appendix A);

   *  runtime enforcement mechanisms outside the skill author's control
      (a given host's tool-approval implementation is out of scope,
      though Section 5 depends on one existing).

1.2.  Relationship to the Base Spec

   The Base Spec [BASESPEC] fixes the physical packaging of a single
   skill: a directory named identically to the skill's name, containing
   a required SKILL.md with YAML frontmatter (name, description,
   optional license, compatibility, metadata, and experimental allowed-
   tools) followed by Markdown instructions, and optional scripts/,
   references/, and assets/ directories.  It also fixes progressive
   disclosure: metadata (~100 tokens) is always resident, the SKILL.md
   body (recommended under 5,000 tokens and under 500 lines) loads only
   once a skill is activated, and files under scripts/, references/, or
   assets/ load only on demand.

   Every requirement in this document is expressed as additional
   structure inside that envelope: fixed sections within the SKILL.md
   body, additional key/value pairs inside the Base Spec's free-form
   metadata map, constraints on the contents of allowed-tools, and one
   family-level extension directory, evals/, that hosts ignore.  This
   document defines no new frontmatter keys at the top level.  Shape
   schemas and the kit live outside any skill package, so a host loading
   a single skill never sees them; a skill therefore cites a shape by
   name first and by path second.

1.3.  Terminology

   The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT",
   "SHOULD", "SHOULD NOT", "RECOMMENDED", "NOT RECOMMENDED", "MAY", and
   "OPTIONAL" in this document are to be interpreted as described in
   BCP 14 [RFC2119] [RFC8174] when, and only when, they appear in all
   capitals, as shown here.

   Skill Family:  a set of skills governed by one instance of this
      specification, sharing one Shape Registry (Section 4.1), one kit
      (Section 9), and one Family Registry File (Section 8.2).

   Family root:  the directory that contains kit/, skills/, and docs/.
      All root-relative paths in this document resolve against the
      family root.  The family root is not necessarily the version-
      control toplevel.

   Query Skill:  a skill whose most severe declared effect is "external-
      read-only" or lower on the Effect Ladder (Section 5.1).  Produces
      an artifact; performs no effect outside itself.

   Command Skill:  a skill whose most severe declared effect is "local-
      write" or higher.  Performs an effect in addition to, or instead
      of, producing an artifact.

   Shape:  a named, versioned, machine-checkable structural type that an
      artifact conforms to (Section 4).

   Stage:  one unit of a skill's Procedure, drawn from the closed
      vocabulary in Section 3.1.

   Rung:  one level of the six-level Effect Ladder.

   Tier:  a skill's priority within its family: pillar or situational.

1.4.  Notational Conventions

   Pipeline composition is written left to right with an arrow: A -> B
   means "the output of A is the input to B."  Optional stages are
   bracketed: [Confirm]; a conditional pair is parenthesized: (Confirm
   -> Act).  A skill's overall type is written as shown below.

   (InputShape) -> Result<OutputShape, FailureShape>

1.5.  Rule Identifiers and Conformance Tags

   Every normative rule in this document is stated as its own paragraph
   headed by a permanent identifier of the form SDS-P-NNN, where P is C
   (core model, Part 0), F (family, Part I), K (kit, Part II), or S
   (skill anatomy, Part III).  Identifiers are never reused; a withdrawn
   rule remains listed as withdrawn.  Each rule also carries a
   requirement level (MUST, SHOULD, or MAY) and exactly one conformance
   tag:

   MACHINE:  checked by the family's linter (Section 9.8).  A
      MUST+MACHINE failure is an error; SHOULD+MACHINE is a warning;
      MAY+MACHINE is informational.

   REVIEW:  requires human judgment; the linter prints these as a
      checklist, never as failures.

   ADVISORY:  guidance; never a conformance failure.

   Appendix B lists every rule with its identifier, slug, section,
   level, and tag; the linter's own rule table MUST match it
   (Section 9.8, Paragraph 2).

1.6.  Document Map

   Part 0 (Section 2 through Section 7) is the conceptual model: what a
   skill is, how its procedure is structured, how skills exchange
   artifacts, and how effects are governed.  Part I (Section 8) is the
   family and repository layer.  Part II (Section 9) is the reference
   kit every family ships.  Part III (Section 10) is the complete
   anatomy of one skill package.  Readers building a skill start at Part
   III and follow its cross-references back into Part 0 for rationale.

2.  Conceptual Model

2.1.  A Skill as a Function

   *SDS-C-001* (MUST, REVIEW) A skill MUST declare five parts:

   Trigger:
      the condition of activation — the Base Spec's description plus an
      explicit statement of when the skill does not apply
      (Section 10.3).

   Inputs:
      the skill's parameters, each marked REQUIRED or OPTIONAL with a
      stated default (Section 6.1).




Steele                    Expires 9 March 2027                  [Page 6]

Internet-Draft                     SDS                    September 2026


   Procedure:
      the ordered body, built from the stage grammar (Section 3).

   Permissions:
      the skill's declared effect contract (Section 5).

   Output:
      a Result — a conforming success Shape, or one of a finite,
      declared set of failure shapes (Section 6.2).

   This model lets two independently-authored skills be reasoned about
   the same way two functions in a typed codebase are: by their
   signature, not by reading their full implementation.

2.2.  Command-Query Separation

   *SDS-C-002* (MUST, REVIEW) A skill MUST obey Command-Query Separation
   [MEYER1988]: it is either a Query Skill (produces information, no
   side effect) or a Command Skill (produces an effect; any information
   it also returns is a report of that effect, not an independent
   analytical artifact).  A skill that both performs a mutating effect
   and produces a materially independent analytical artifact MUST be
   split into a Query Skill feeding a Command Skill via the pipe
   composition rule in Section 3.2.

2.3.  Purity, Referential Transparency, and Idempotence

   *SDS-C-003* (MUST, REVIEW) A Query Skill's Procedure is pure with
   respect to its declared Inputs: given the same Inputs and no
   undeclared ambient state (the current date, network state not listed
   as an Input, files not listed as an Input), it MUST produce the same
   Output.  This is a hermeticity requirement on the Gather stage: a
   Query Skill's Gather stage MUST read only what its Inputs declaration
   lists.  A skill satisfying this is _referentially transparent_: any
   invocation MAY be replaced, anywhere in a pipeline, by its
   previously-computed Output for the same Inputs.  Referential
   transparency is the single property that licenses caching, reordering
   (Section 3.4), and parallel execution.

   *SDS-C-004* (MAY, ADVISORY) metadata.idempotent declares the weaker
   property "safe to re-call with identical arguments," matching the
   Model Context Protocol's idempotentHint [MCPANNOT].  It does not
   declare, and does not trigger, the fixed-point composition law
   (Section 3.4, Paragraph 4); a Command Skill can be idempotent in this
   sense (opening an already-open PR is a no-op) without being pure.

Internet-Draft                     SDS                    September 2026


2.4.  Totality

   *SDS-C-005* (MUST, REVIEW) A skill's declared behavior MUST be total
   over its declared Input domain: for every input satisfying its stated
   preconditions, including boundary cases (empty input, a single item,
   the maximum stated size, malformed-but-precondition-satisfying
   input), the skill MUST have a defined, non-crashing Output — either a
   success Shape or a declared failure Shape.  Undefined behavior on a
   precondition-satisfying input is a specification defect, not an
   implementation gap.

3.2.  Canonical Pipelines

   *SDS-C-011* (MUST, REVIEW) A Query Skill's Procedure MUST reduce to
   the Query pipeline.  Filter and Classify are optional and MAY be
   omitted entirely.

   *SDS-C-012* (MUST, REVIEW) A Command Skill's Procedure MUST reduce to
   the Command pipeline.  The parenthesized Confirm/Act pair is
   _conditional_: it MAY be skipped on an invocation only by a branch
   declared in Decide, per Section 10.4; both headings are retained.
   Communicate and Persist headings are always present (Section 10.3,
   Paragraph 4).

   Query pipeline (a Query Skill):

      Gather -> [Filter] -> Analyze -> [Classify] -> Synthesize

   Command pipeline (a Command Skill):

      Gather -> Analyze -> Decide -> (Confirm -> Act)
         -> [Communicate] -> [Persist]

   *SDS-C-013* (MUST, REVIEW) Nothing MAY follow Synthesize in a Query
   pipeline that touches state outside the produced artifact; a
   Procedure that does so is, by definition, a Command Skill and MUST be
   labeled and gated as one.

3.3.  Composition Semantics

   *SDS-C-014* (MUST, REVIEW) Stage composition within a Procedure, and
   skill composition within a pipeline, follows railway-oriented
   composition [WLASCHIN]: every stage returns a success value or a
   failure value.  A failure at any stage MUST short-circuit every
   subsequent stage and proceed directly to the declared failure Output
   (Section 6.2).  A Procedure or orchestrator MUST NOT require per-
   stage bespoke "what if the prior stage failed" logic.

3.4.  Composition Laws

   The following laws hold for a Query Skill's Procedure and are checked
   by the eval table (Section 10.9).

   *SDS-C-015* (MUST, REVIEW) Identity.  Composing a skill with the
   identity transform MUST leave its behavior unchanged in either order.
   An empty-result Output (Section 4.3) is the identity element of its
   Shape and MUST be handled by downstream consumers via their ordinary
   code path.




Steele                    Expires 9 March 2027                 [Page 10]

Internet-Draft                     SDS                    September 2026


   *SDS-C-016* (MUST, REVIEW) Associativity.  For composable stages f,
   g, h: (f -> g) -> h MUST equal f -> (g -> h).  Lossy reduction ("keep
   only the top N") MUST occur only once, at the final Synthesize stage;
   intermediate combination MUST be lossless.

   *SDS-C-017* (MUST, REVIEW) Fixed point.  Where a skill's shape-out
   equals its shape-in and both name a registered Shape, applying the
   skill to its own Output a second time MUST produce no further change.
   freeform paired with freeform does not qualify: freeform is the
   declared absence of structure, not a structure an output can be fed
   back into. metadata.idempotent does not trigger this law
   (Section 2.3, Paragraph 2).  Machine check: Section 10.9, Paragraph
   5.

   *SDS-C-018* (MUST, REVIEW) Map fusion.  Where a skill is applied
   across a collection, map(f) -> map(g) MUST equal map(f -> g).  Where
   it does not, the two stages have a hidden dependency and MUST NOT be
   fused into a single parallel pass.

3.5.  Fail-Fast Validation

   *SDS-C-019* (MUST, REVIEW) A Procedure MUST validate every stated
   precondition as its first action, before Gather proceeds.  A
   violation MUST produce an immediate, specific failure naming the
   unmet precondition, mapped to a declared @throws code; it MUST NOT be
   discovered partway through Analyze or later.

3.6.  Termination Requirements

   *SDS-C-020* (MUST, REVIEW) Any stage that iterates internally MUST
   declare an explicit termination condition: a convergence check or a
   stated maximum number of iterations.  Open-ended iteration with no
   declared termination condition is nonconformant.

4.  Artifact Shapes and Interchange

4.1.  The Shape Registry

   Skills compose by agreeing on the structure of what they exchange,
   never by one skill invoking another directly.  Each family maintains
   a Shape Registry: the set of kit/shapes/<name>.schema.json files
   (Section 9.3).

   *SDS-C-030* (MUST, REVIEW) A skill's @returns and @requires MUST name
   a registered Shape, or explicitly declare freeform where no
   structural contract is offered.  Machine checks: Section 10.2,
   Paragraph 18, Section 10.3, Paragraph 10.




Steele                    Expires 9 March 2027                 [Page 11]

Internet-Draft                     SDS                    September 2026


4.2.  The Standards-First Rule

   *SDS-C-031* (MUST, REVIEW) Before registering a new Shape, the family
   MUST check whether an established external interchange format already
   exists for that category of artifact in the family's domain, and
   adopt or wrap it rather than defining a competing bespoke structure.
   Illustrative software-development examples: SARIF [SARIF] for
   finding-style results, the OSV schema [OSV] for vulnerability
   records, SPDX [SPDX] or CycloneDX [CYCLONEDX] for dependency
   manifests, MADR [MADR] for decision records, the C4 model [C4MODEL]
   for architecture diagrams, Diataxis [DIATAXIS] for documentation
   quadrants, OpenTelemetry semantic conventions [OTELSEMCONV] for
   observability fields, the Twelve-Factor App [TWELVEFACTOR] rubric for
   environment checks, and Conventional Commits [CONVCOMMITS] with Keep
   a Changelog [KEEPACHANGELOG] for release-note generation.  Each
   registered Shape has a machine-checkable JSON Schema [JSONSCHEMA]
   (Section 9.3, Paragraph 1).

4.3.  The Null Object Requirement

   *SDS-C-033* (MUST, REVIEW) A skill whose Analyze/Classify stage finds
   nothing MUST still produce a fully well-formed, schema-valid instance
   of its declared Shape with zero entries — never null, an empty
   string, an omitted file, or a distinct "nothing found" format (the
   Null Object pattern [GOF-ADJACENT]).

4.4.  Immutability and Supersession

   *SDS-C-034* (SHOULD, REVIEW) Once persisted, an artifact instance
   SHOULD be treated as immutable.  Where a later invocation would
   otherwise update a decision- or plan-shaped artifact, it MUST persist
   a new, dated instance referencing the instance it supersedes (the
   superseded by convention established by MADR [MADR]).

5.  Effects, Permissions, and Safety

5.1.  The Effect Ladder

   *SDS-C-040* (MUST, REVIEW) Each skill MUST declare, in
   metadata.effect-tier, the single highest rung its Procedure reaches
   on the following ordered ladder.

   1.  local-read-only (reads only the local filesystem)

   2.  domain-read-only (reads a closed, predictable domain, e.g.
       version-controlled repository history)





Steele                    Expires 9 March 2027                 [Page 12]

Internet-Draft                     SDS                    September 2026


   3.  external-read-only (reads an open-world external system: a
       network API, a live service)

   4.  local-write (writes only the skill's own declared output
       location)

   5.  shared-write (writes to, or notifies, something other skills,
       people, or systems depend on)

   6.  irreversible (an effect that cannot be undone by a compensating
       action, or whose undo is itself irreversible)

   *SDS-C-041* (MUST, REVIEW) Rungs 1 through 3 define a Query Skill;
   rungs 4 through 6 define a Command Skill.  A skill at rung 5 or 6
   MUST include a Confirm stage.  Machine check: Section 10.2, Paragraph
   17.

5.2.  Relationship to MCP Tool Annotations

   *SDS-C-042* (SHOULD, ADVISORY) Where a skill is exposed as, or
   invokes, a Model Context Protocol tool, its rung SHOULD be reflected
   in that tool's annotations [MCPANNOT]: readOnlyHint for rungs 1-3,
   destructiveHint for rung 6, idempotentHint for the
   metadata.idempotent declaration, and openWorldHint for rung 3 or any
   rung reached via an external system.

5.3.  Permission Scoping

   *SDS-C-043* (MUST, REVIEW) allowed-tools is scoped by rung, not by
   kind.  Any skill whose Procedure reaches rung 2 or above and invokes
   any tool or bundled script MUST declare a narrow scope; operations
   that would place the skill at rung 5 or 6 MUST NOT appear in it under
   any kind, so that mis-scoping cannot suppress the host's own approval
   mechanism.  Machine checks: Section 10.2, Paragraph 12 through
   Section 10.2, Paragraph 15.

5.4.  Confirmation Gates

   *SDS-C-044* (MUST, REVIEW) A Confirm stage functions as middleware in
   front of Act: it MUST run on every invocation that reaches an Act at
   rung 5 or above, MUST NOT be skipped because an equivalent
   confirmation was granted earlier in the session, and MUST state
   concretely what specific effect is about to occur.








Steele                    Expires 9 March 2027                 [Page 13]

Internet-Draft                     SDS                    September 2026


5.5.  Compensating Actions

   *SDS-C-045* (MUST, REVIEW) Each mutating step of an Act stage MUST
   have a declared compensating action, to be taken if a later step in
   the same sequence fails (the saga pattern [SAGA]).  Where none
   exists, the step MUST say so and be sequenced last.

5.6.  Check-Before-Act and Checkpointing

   *SDS-C-046* (MUST, REVIEW) Every mutating step MUST verify current
   state before mutating and MUST skip as an explicit no-op when the
   effect is already applied, so that re-invocation after an
   interruption is safe rather than duplicative.

   *SDS-C-047* (MUST, REVIEW) A Command Skill MUST persist a two-phase
   checkpoint for each mutating step, written before the step and
   updated after it, so that resumption after an interruption is well-
   defined.  The record format and location are specified in
   Section 10.10; machine check: Section 10.5, Paragraph 4.

5.7.  Trust Model for Declared Hints

   *SDS-C-048* (MUST, ADVISORY) Effect Ladder rungs, MCP annotations,
   and allowed-tools scopes are declared hints.  A host MUST NOT treat a
   skill's own declaration as the sole safety control; declared risk,
   permission scoping, and host-level approval are independently
   redundant controls (defense in depth), per the caution that
   annotation hints are untrusted unless sourced from a trusted party
   [MCPANNOT].

6.  Contracts

6.1.  Precondition/Postcondition Notation

   *SDS-C-050* (MUST, REVIEW) Following Design by Contract [MEYER1992],
   every skill MUST state @requires (preconditions as testable
   assertions), @returns (the guarantee about a successful Output,
   naming a Shape), and @throws (every declared failure mode, exhaustive
   with respect to Section 2.4, Paragraph 1).  Machine check:
   Section 10.3, Paragraph 1.

   *SDS-C-051* (MUST, REVIEW) Each precondition MUST be marked REQUIRED
   or OPTIONAL with a stated default.  Machine check: Section 10.3,
   Paragraph 8.







Steele                    Expires 9 March 2027                 [Page 14]

Internet-Draft                     SDS                    September 2026


   *SDS-C-052* (MUST, REVIEW) A skill declaring more than five REQUIRED
   inputs MUST be split into narrower skills or take one bundled Shape
   instead (the long-parameter-list smell).  Machine check:
   Section 10.3, Paragraph 9.

6.2.  The Result Type and Failure Modes

   A skill's Output is modeled as shown below.

   Result<Success, Failure>

   *SDS-C-053* (MUST, REVIEW) A Failure value MUST preserve the causal
   chain of what was being attempted at each level, in the style of
   wrapped errors in idiomatic Go [ERRWRAP] ("could not produce X: could
   not read Y: reason"), rather than surfacing only the innermost cause
   or only a generic top-level message.

6.3.  Substitutability

   *SDS-C-054* (MUST, REVIEW) A skill published as a replacement for
   another MUST satisfy the Liskov Substitution Principle [LSP] against
   every declared consumer of the original: preconditions no stronger,
   postconditions no weaker.  A version increment alone does not
   establish substitutability; it MUST be verified against declared
   consumers.

7.  Composition and Reuse Patterns

7.1.  Functional Core, Imperative Shell

   *SDS-C-060* (SHOULD, REVIEW) An orchestrating Command Skill SHOULD
   contain no Analyze, Classify, or Decide logic of its own [BERNHARDT];
   that reasoning belongs in a Query Skill it invokes via a Delegate
   stage.  The orchestrator's own Procedure reduces to: delegate for a
   decision artifact, Confirm, Act.

7.2.  Specialization via Injection

   *SDS-C-061* (MUST, REVIEW) A skill MUST NOT be forked to specialize
   it for one context.  Context-specific configuration MUST be supplied
   via assets/ or compatibility as an injected dependency [DI], with the
   Procedure written against the abstract presence of that dependency.









Steele                    Expires 9 March 2027                 [Page 15]

Internet-Draft                     SDS                    September 2026


7.3.  Migration via the Strangler Fig Pattern

   *SDS-C-062* (MUST, REVIEW) Adoption of a new Shape, standard, or
   convention across an existing family MUST proceed incrementally
   [FOWLER-STRANGLER]: revised skills adopt it directly; an Adapter (a
   judgment-free translation script) bridges unmigrated output; the
   Adapter is retired once no unmigrated skill remains.

7.4.  Consumer-Driven Contract Testing

   *SDS-C-063* (SHOULD, REVIEW) Where two skills are designed to chain,
   the eval suite SHOULD include a consumer-driven contract test [PACT]:
   the producer is run for real and its actual Output validated against
   the consumer's declared @requires schema.  Per-skill evals passing in
   isolation MUST NOT be treated as evidence that two skills chain
   correctly.

   *SDS-S-051* (MUST, MACHINE) A rung-5 or rung-6 Act MUST be issued as
   a direct, unwrapped tool call after Confirm.  It MUST NOT be
   delegated to a bundled script, because pre-approving the script pre-
   approves the mutation and silently bypasses the gate.  A script in a
   skill at rung 5 or higher MUST NOT invoke a mutating command via a
   subprocess.

   *SDS-S-052* (MUST, REVIEW) Act MUST state the check-before-act no-op
   skip explicitly (Section 5.6, Paragraph 1).

   *SDS-S-053* (MUST, MACHINE) A rung-4-or-higher Act section MUST
   contain a **Checkpoint** label describing the two-phase record of
   Section 10.10: written with status: pending before the mutating call,
   updated to status: completed immediately after it succeeds.  A



Steele                    Expires 9 March 2027                 [Page 24]

Internet-Draft                     SDS                    September 2026


   resumed invocation reading pending MUST treat the step as possibly
   applied and check-before-act; reading completed MUST skip the step.
   Single-step Command Skills MUST checkpoint: the pending record is
   what makes the compensating action executable.

   *SDS-S-054* (MUST, MACHINE) A rung-4-or-higher Act section MUST
   contain a **Compensating action** label for each mutating step
   (Section 5.5, Paragraph 1).

   *SDS-S-055* (SHOULD, REVIEW) A skill with one mutating step SHOULD
   write its checkpoint inline; a skill with two or more SHOULD use
   scripts/checkpoint.py.

   *SDS-S-056* (SHOULD, REVIEW) A mutating call in an Act section SHOULD
   name its target explicitly — the repository (-R owner/repo), the
   branch (--head), the state directory (--state-dir) — rather than
   relying on the working directory, and the Act's commands SHOULD all
   run from the skill directory.  Changing directory between the pending
   record, the mutation, and the completed record breaks the skill-
   relative script paths of Section 8.4, Paragraph 2 and leaves a
   pending record after a successful mutation; observed in a live run of
   release-publisher.

10.6.  scripts/

   *SDS-S-060* (MUST, REVIEW) A sub-step MUST be a script when it is
   deterministic, mechanical, and requires no interpretation of
   ambiguous input (the toil test [SRE-EB]): parsing a real grammar,
   calling an external system and normalizing its response, or
   translating one format to another (an Adapter).

   *SDS-S-061* (MUST, REVIEW) Analyze, Classify, and Decide MUST NOT
   live in a script; a script cannot exercise judgment.

   *SDS-S-062* (SHOULD, MACHINE) Files under scripts/ SHOULD be
   snake_case verb-noun names (parse_manifest.py); an Adapter names both
   sides (osv_to_finding.py).  This rule does not apply to fixture
   generators under evals/fixtures/.

   *SDS-S-063* (MUST, MACHINE) Every script MUST begin with a shebang
   and carry a module docstring (or a leading comment block for shell);
   it prints JSON to stdout, exits 0 with an empty instance on empty
   input, and exits 1 with an ERROR: line on stderr on failure (the
   presence of error handling is checked as a warning).

   *SDS-S-064* (MUST, REVIEW) Any dependency beyond the standard library
   MUST be named in the script's docstring and in compatibility.




Steele                    Expires 9 March 2027                 [Page 25]

Internet-Draft                     SDS                    September 2026


   *SDS-S-065* (SHOULD, MACHINE) A script that calls an external system
   SHOULD expose a --<thing>-file flag substituting a fixture for the
   live call, so that evals exercise the same code path offline.

   *SDS-S-066* (SHOULD, MACHINE) Scripts SHOULD carry the owner execute
   bit.

   *SDS-S-067* (SHOULD, MACHINE) Every file under scripts/ SHOULD be
   referenced from SKILL.md.

10.7.  references/

   *SDS-S-070* (MUST, REVIEW) Content needed on every invocation MUST
   live in SKILL.md; content needed only sometimes MUST live under
   references/, loaded on demand.

   *SDS-S-071* (SHOULD, MACHINE) A file under references/ SHOULD NOT
   link to another file under references/ (one level deep).

   *SDS-S-072* (SHOULD, MACHINE) Each SKILL.md pointer to references/
   SHOULD be phrased as a condition ("If unsure why X, consult ..."),
   not a blanket instruction.

   *SDS-S-073* (SHOULD, MACHINE) Every file under references/ SHOULD be
   linked from SKILL.md.

10.8.  assets/

   *SDS-S-080* (MUST, MACHINE) assets/ MUST NOT contain a copy of a
   family Shape schema; reference kit/shapes/ directly.

   *SDS-S-081* (MUST, MACHINE) Every assets/ file the Procedure reads
   MUST be named in @requires or Instructions; it is a declared input
   for hermeticity (Section 2.3, Paragraph 1).

   *SDS-S-082* (MUST, REVIEW) Per-installation configuration MUST be
   injected via assets/, never by forking (Section 7.2, Paragraph 1).

10.9.  evals/ and Fixtures

   *SDS-S-090* (MUST, MACHINE) The eval file MUST parse; skill MUST
   equal name; rows MUST be non-empty with unique names; each
   expected.kind MUST be success, failure, or not-applicable; a not-
   applicable row MUST carry a non-empty reason; a failure row MUST
   carry failureCode; any YAML document after the first MUST be empty
   (the smoke section is comments).





Steele                    Expires 9 March 2027                 [Page 26]

Internet-Draft                     SDS                    September 2026


   *SDS-S-091* (SHOULD, MACHINE) A success row SHOULD carry at least one
   assertion about content or shape and, for a registered Shape, a shape
   field.  "Runs without erroring" is not a passing eval.

   *SDS-S-092* (MUST, MACHINE) For a skill at rung 3 or higher, no
   required row MUST invoke a live external system (curl, wget, http://,
   https://, gh api, pip install, npm install).  Live checks live after
   the --- document separator as a non-blocking smoke test asserting
   shape only, never specific content, because the content of an open-
   world system changes for reasons unrelated to the skill's
   correctness.

   *SDS-S-093* (SHOULD, MACHINE) A frozen recording of a real external
   response SHOULD be named evals/fixtures/frozen-<source>-<what>.json,
   captured once and never refreshed by the evals.

   *SDS-S-094* (MUST, MACHINE) A row named fixed-point MUST exist.  It
   is a success row iff shape-out equals shape-in and both are
   registered Shapes (Section 3.4, Paragraph 4); otherwise it is not-
   applicable with the reason stated.

   *SDS-S-095* (MUST, MACHINE) A row named mutation-fixture MUST exist.
   It is a success row referencing an evals/fixtures/ path with a
   deliberately planted instance of what the skill detects iff shape-out
   is finding-list; otherwise it is not-applicable with the reason
   stated.

   *SDS-S-096* (MUST, MACHINE) Static fixtures live in evals/
   fixtures/<case>/, with .gitkeep marking an intentionally empty case.
   A fixture that is itself a version-control repository MUST NOT be
   checked in; it MUST be produced by an executable, idempotent
   evals/fixtures/build-<name>.sh whose output directory is listed in
   evals/fixtures/.gitignore.  Any nested .git under fixtures MUST be
   ignored.  Every fixture path a row references MUST exist or be
   generated.

   *SDS-S-097* (SHOULD, MACHINE) Every fixture file SHOULD be referenced
   by a row or by the smoke section.

   *SDS-S-098* (MUST, MACHINE) Rows MUST reference only paths inside the
   skill directory or under kit/; absolute paths and ~ are reported as
   non-hermetic.

   *SDS-S-099* (MUST, MACHINE) The table MUST contain a success row
   named happy-path*; at least two boundary-* rows, one a success on
   empty/zero/minimal input and one a failure on malformed/invalid/
   missing input; and a row named contract-with-* (Section 7.4,
   Paragraph 1), which MAY be not-applicable with a reason.  Evals
   follow the table-driven convention [GOTESTING].

10.10.  Runtime State

   *SDS-S-100* (MUST, MACHINE) A Command Skill's runtime state MUST live
   at <family-root>/.skills-state/<name>/<key>.json, where <key>
   uniquely identifies the invocation (a PR number, a branch, a
   migration id); the skill's Act section names this path.  Referencing
   another skill's state directory is an error.  The family root is the
   root of the skill family's own checkout, not of the repository the
   skill is operating on: when a skill runs inside some other repository
   (the normal case for a GitHub-operating skill), its state still lives
   under the family's .skills-state/, and a bundled checkpoint script
   MUST accept an explicit state directory for exactly that situation
   rather than assuming the working directory is inside the family.

   *SDS-S-101* (MUST, REVIEW) The checkpoint record MUST have the
   following form.

   {
     "key": "<invocation key>",
     "step": "<mutating step name>",
     "status": "pending" | "completed",
     "startedAt": "<ISO-8601>",
     "preState": { ... },
     "compensatingAction": "<what undoes this step>",
     "postState": { ... }   // present only when completed
   }

10.11.  Validation Gate

   *SDS-S-110* (MUST, REVIEW) A skill is done only when: (0) the linter
   passes with no errors; (1) metadata matches what the Procedure
   actually does; (2) an example artifact validates against its Shape's
   schema; (3) every eval row passes, including the mutation fixture and
   fixed-point row where required; and (4) the glossary check passes.
   If any fails, fix the skill — not the eval, and not the glossary.

11.  Security Considerations

   This specification is, in large part, a security specification, and
   Section 5 together with Section 10.5 is its core normative content.
   The following risks are called out explicitly:



Steele                    Expires 9 March 2027                 [Page 28]

Internet-Draft                     SDS                    September 2026


   *  Declared hints (Effect Ladder rung, MCP annotations, allowed-
      tools) are self-reported and MUST be treated as untrusted absent a
      trusted source (Section 5.7).  A mis-declared rung is a directly
      exploitable path to bypassing confirmation.

   *  A pre-approved script that performs a mutation is a bypassed gate
      (Section 10.5, Paragraph 2): the host approves "run this script,"
      and the script, not the model's next tool call, performs the
      effect.

   *  Content gathered from an open-world source during a Query stage
      may later inform a Decide or Act stage.  It MUST be treated as
      data, not instruction; a Procedure MUST NOT follow directives
      inside gathered content.

   *  Fixtures, including frozen recordings of external responses, are
      untrusted data of the same kind and MUST NOT be executed or
      followed as instruction.

   *  Bundled scripts/ are executable code with the supply-chain risk of
      any third-party code; a family SHOULD review and pin them like a
      dependency.

   *  Overly broad allowed-tools scoping does not merely fail to add
      safety; it suppresses the host's own confirmation mechanism from
      engaging.

   *  Compensating actions are themselves effects and MUST meet the same
      confirmation requirements as the action they undo when they sit at
      rung 5 or above.

12.  Registry Considerations

   This specification establishes the following registries, each
   maintained by a family for itself:

   Shape Registry (Section 4.1):
      new entries require a Standards-First check (Section 4.2,
      Paragraph 1), a machine-checkable schema (Section 9.3, Paragraph
      1), and a defined zero-entry form (Section 4.3, Paragraph 1);
      changes follow Section 8.5, Paragraph 2.

   Family Registry (Section 8.2):
      one entry per skill, planned or built, validated against its
      schema; the only source for generated indexes.

   Effect Ladder (Section 5.1):
      six fixed rungs.  A family MUST NOT reorder them but MAY define

Appendix C.  Change Log

   *1.0-draft, revision 02 (2026-09-06):* Folds in what building the
   twenty-eight situational skills and two more live runs taught.  SDS-
   F-061 now exempts a glossary term that is part of a proper noun or an
   identifier (the GitHub cluster's own nouns — issue, Projects, board
   item — were unspeakable under the bare heuristic; the glossary gained
   rows for them).  SDS-F-031 now lets a consumer-driven contract row
   run another skill's script by its family-root-relative path, because



Steele                    Expires 9 March 2027                 [Page 40]

Internet-Draft                     SDS                    September 2026


   the strongest contract is the real consumer (rfc-writer renders, then
   design-doc-review's own script must find nothing).  New SDS-S-056
   (SHOULD, REVIEW): a mutating call names its target explicitly rather
   than relying on the working directory.  The linter's heuristics
   changed to match; one REVIEW rule was added to Appendix B; no MACHINE
   rule was added or removed.

   *1.0-draft, editorial (2026-09-06):* SDS-S-100 now states that the
   family root is the skill family's own checkout, not the repository a
   skill operates on, and that a bundled checkpoint script must accept
   an explicit state directory — observed while driving pr-lifecycle-
   manager against a separate repository.  No rule was added, removed,
   or re-tagged; Appendix B is unchanged.

   *1.0-draft (2026-09-05):* Restructured top to bottom into Part 0
   (core model), Part I (family and repository), Part II (kit), and Part
   III (skill anatomy); every normative rule now carries a permanent
   identifier and a MACHINE/REVIEW/ADVISORY tag, indexed in Appendix B;
   added the conformance linter contract.  Resolved nine drift findings
   against the kit and the two worked skills: (1) the fixed-point law is
   gated on a registered shape-out equal to shape-in, not on idempotent;
   (2) checkpointing is two-phase — a pending record written before the
   mutating call, updated to completed after — and single-step Command
   Skills must checkpoint; (3) metadata has exactly seven string keys;
   (4) allowed-tools is required by rung, not kind, with two declared
   sources; (5) tier vocabulary is pillar / situational; (6) a
   conditional Act path is a permitted Command form with Confirm/Act
   headings retained and Communicate/ Persist always present; (7) the
   registry is kit/registry/marketplace.json with required shape-in/
   shape-out, status, and a top-level sds version (the former example
   registry file name is retired); (8) all cross-references are family-
   root-relative; (9) fixtures have a defined layout with generated
   repositories, frozen recordings, and a no-live-call rule for open-
   world stages.  Also added: the checkpoint state path, the prohibition
   on wrapping a rung-5/6 Act in a pre-approved script, script and
   reference conventions, the long-parameter-list rule, and the
   validation gate.

   *0.3 (2026-09-05):* Rebuilt in xml2rfc version 3 (RFC 7991)
   vocabulary in place of the plain-text RFC-style draft.  No normative
   changes from 0.2.
